# 性能实测

> 全部数据来自本机实测，**没有引用任何厂商宣传口径**。每一项都写明了测试方法与口径修正过程，
> 便于独立复核。凡是拿不到可信数据的地方，直接标注为「未取得」，不做填充、不做估算。

## 测试环境

| 项 | 值 |
|---|---|
| 操作系统 | Windows 10 IoT Enterprise LTSC **21H2（Build 19044）**，x64 |
| CPU | AMD **Ryzen 7 7435H**，8 核 16 线程，3.1 GHz |
| 内存 | 16 GB |
| 磁盘 | 2 块 NVMe SSD：disk 0 → `D:`，disk 1 → `C:`（系统）与 `E:`（数据） |
| 文件系统 | NTFS |
| ZenFile | `0.3 Beta`，单文件 **1,494,016 字节**（数据采集时），`--release` 构建 |
| Pulse | `1.0.53.0`，`pulse.exe` 9,155,072 字节；另带常驻后台索引进程 `Pulse.Index.exe` |
| Explorer | Windows 10 LTSC 自带 |

::: tip Pulse 的后台开销
它有一个常驻索引服务 `Pulse.Index.exe`（测量期间占 **79～821 MB**，随索引进度波动）。
本页 Pulse 的主进程内存**不含**该服务；但这解释了它为何冷搜最快——
代价是常驻内存与后台 IO。
:::

## 方法学

### 三条硬原则

1. **三方交错采样**（A/B/A 轮换），而不是「测完 A 再测 B 再测 C」。
   本机 SSD 性能会随系统负载漂移——同一软件前后两次最大差了 **3 倍**，不交错会产出假结论。
2. **取中位数**，不取均值，避免单次抖动把结论带偏。
3. **每轮的目录都是新的**：每个被测对象每次都用一个**从未被访问过**的专属目录，
   避开 Shell bag / 文件系统缓存 / 目录元数据 cache 带来的「第二次更快」假象。

### 口径修正 ①：大文件复制不能看「目标文件长度达标」

ZenFile 与 Explorer 都采用「先预占长度、再填充数据」（`set_len` / `SetEndOfFile`）。
于是目标文件在 **0.2 秒内就显示成 4.7 GB**，此时数据其实还完全没写。

早期按「文件大小达标」判定，得到过 **explorer 0.203 秒复制 4GB（= 20143 MB/s）**
这种超过 SSD 物理能力的荒谬数字。

改用两级判据：

| 判据 | 定义 | 是否用于排名 |
|---|---|---|
| `t_size` | 目标文件名义长度达到源长度的耗时 | ❌ 仅作对照展示 |
| **`t_land`** | 用 `FILE_FLAG_NO_BUFFERING` **绕过系统缓存**直读目标尾段、与源比对一致的第一时刻 | ✅ 唯一排名口径 |

### 口径修正 ②：必须是跨物理磁盘

早期素材是在 C: 内部同卷同盘生成再复制的，Windows 的缓存与文件系统优化会把真实写盘成本盖掉。
改为 **`E:`（disk 1）→ `D:`（disk 0）**，两块不同的物理 SSD。

## 六项对比（中位数）

### 1. 内存占用（打开首页静置 15 秒）

| 指标 | ZenFile | Explorer | Pulse |
|---|---:|---:|---:|
| RSS（工作集） | **29.5 MB** | 54.7 MB | 214.5 MB |
| 私有工作集 | **14.6 MB** | 21.1 MB | 217.6 MB |
| 进程数 | 1 | 1 | 3 |

::: warning Explorer 的读数需要解释
`explorer.exe` 是常驻 shell（还负责桌面与任务栏），它的 RSS 不能全部算作
「这个文件窗口的开销」。实测 Explorer 会为文件窗口**另起独立进程**：

```
shell 常驻进程: 140.5 MB（与本次浏览无关，一直存在）
文件窗口进程: 46.9 MB（基线） → 86.3 MB（打开 10 万文件的目录）
```

所以 Explorer 可比的数字是 **46.9 → 86.3 MB**。即便按这个更保守的口径，
ZenFile 仍是三者中最省的。
:::

### 2. 多文件操作速度（1 万个 4KB 小文件 = 40 MB，同盘）

| 指标 | ZenFile | Explorer | Pulse |
|---|---:|---:|---:|
| 粘贴完成（秒） | **1.957** | 14.876 | 9.623 |
| 总耗时（秒） | **3.261** | 16.181 | 10.926 |
| 吞吐（文件/秒） | **5109** | 672 | 1039 |

领先 **7.6 倍**（vs Explorer）／**4.9 倍**（vs Pulse）。三轮数据离散度小于 5%，结论稳定。

### 3. 单个大文件操作速度（真实 Windows 镜像，跨物理盘）

| 指标 | ZenFile | Explorer | Pulse |
|---|---:|---:|---:|
| 耗时 | 5.78 s | 5.89 s | **4.23 s** |
| CPU/GiB | **0.376** | — | 1.47 |
| 峰值线程 | 21 | — | 99 |

**已追平 Explorer**，且 CPU/GiB 是三者最低。剩下唯一的差距是 Pulse，
代价是它的 1.47 CPU/GiB 与 99 个线程。

### 4. 文件查找速度（10 万文件树中按文件名找 1 个文件）

| 指标 | ZenFile | Explorer | Pulse |
|---|---:|---:|---:|
| 冷搜（秒） | 0.856 | 1.167 | **0.704** |
| 热搜（秒） | 0.726 | **0.701** | 0.706 |
| 搜索时 RSS（MB） | 104.1 | **69.7** | 279.9 |

三者在同一量级（0.7～1.2 秒），**差异不大**。Pulse 靠常驻索引服务拿到冷搜第一，
代价是 279.9 MB 的进程内存 + 后台 79～821 MB 的索引服务。ZenFile 不建常驻索引，冷搜仍快于 Explorer。

### 5. 大量文件加载速度（单目录 10 万文件，冷打开）

| 指标 | ZenFile | Explorer | Pulse |
|---|---:|---:|---:|
| 窗口出现（秒） | **0.027** | 0.177 | 0.177 |
| 首帧内容（秒） | **0.024** | 0.084 | 0.118 |
| 画面收敛（秒） | 0.454 | **0.443** | 0.791 |
| 总耗时（秒） | **0.481** | 0.620 | 0.967 |
| 加载后 RSS（MB） | **57.6** | 91.5 | 173.2 |

窗口出现与首帧内容几乎在按下回车的同时完成，比另两者快 3～6 倍。

### 6. 文件夹占用大小的计算速度（2 万文件 / 78.1 MB）

| 指标 | ZenFile | Explorer | Pulse |
|---|---:|---:|---:|
| **大小算完（秒）** | **0.565** | 0.685 ⚠ | 0.666 |
| 扫描期峰值 RSS（MB） | **31.1** | 63.1 ⚠ | 258～280 |

⚠ Explorer 只有 1 个有效样本，仅供参考。

加了一个下界锚点：Python `os.walk` 遍历同一目录需 0.82～0.87 s，
**三家的计算时间都比 Python 裸遍历还快**，说明这项比的就是递归遍历本身的执行效率。
ZenFile 的 0.565 s 最接近「纯遍历成本」，峰值内存只有 Pulse 的 **1/8**。

### 6.5 目录复制前的规划扫描（10 万条目）

这一项**没有三方对照**，只有 ZenFile 自己的前后对比。

| 臂 | 耗时 | 每条目 | 峰值工作集 |
|---|---:|---:|---:|
| `naive`（旧生产） | 3.07 s | 30.7 µs | 44 MB |
| `enumonly`（纯枚举下界） | 0.033 s | 0.33 µs | 2 MB |
| `prod`（优化前） | 0.94 s | 9.4 µs | 43 MB |
| **`prod`（优化后，生产代码实测）** | **0.233 s** | **2.3 µs** | **43 MB** |

**净提升 13 倍**，3 轮交错 A/B，取中位数。

::: danger 一次必须说清楚的过程失误
早期版本这里写的是「3.25 s → 0.040 s，**86 倍**」。那个数字**是错的**：

1. 基准的 engine 臂把扫描逻辑在 benchmark 里**重抄了一遍**，而生产 `collect()`
   的文件分支当时还走 `src.symlink_metadata()`——基准测的是一条产品还没走上的路。
   现在 engine 臂**直接调 `pub fn plan_only()`**，基准和产品不可能再各自漂移。
2. 即便在重抄的那条路上，也只对上了第一半。第二半的差距来自 `resolve_conflict`
   里**每个条目一次 `Path::exists()`**：那是一次完整的文件系统查询，
   10 万条目就是 10 万次。拆成三臂后真相才暴露——`enumonly`(0.033 s) 与
   `prod`(0.94 s) 之间的 0.9 s **全在存在性查询上，与文件系统无关**。

修法是 `ExistCache`：按目录缓存一次 `read_dir` 快照，每目录只付一次枚举。
:::

## UI 响应性

「速度」不只有墙钟时间。一项操作如果在主线程上同步跑，
**整个窗口会僵住**，用户感知到的慢比计时器上的数字难看得多。

判据用 `WM_NULL` 的**往返延迟**（`SendMessageTimeoutW`，5 秒超时即判卡死），不看操作结果。

**删除**（20 000 文件 / 20 子目录）：

| 阶段 | p50 | p95 | worst | 卡死 |
|---|---:|---:|---:|---:|
| 空闲基线 | 0.1 ms | 0.2 ms | 0.7 ms | 0 |
| **删除中** | **0.0 ms** | **4.8 ms** | **5.5 ms** | **0** |
| 删除后 | 0.1 ms | 0.3 ms | 0.3 ms | 0 |

删除本身耗时 3.3 s，期间主窗口还能切换目录（1.2 s 内列表刷新）——
即不只是「没卡死」，而是真的在处理用户操作。

**批量重命名**（3 000 文件）：重命名中 p50 = 0.1 ms、p95 = 0.3 ms、卡死 0。

## 结论速览

| 项目 | 第一名 | ZenFile 的相对表现 |
|---|---|---|
| 内存占用 | **ZenFile**（29.5 MB） | 领先，约为 Pulse 的 1/7 |
| 多文件操作 | **ZenFile**（5109 文件/秒） | 领先 Explorer **7.6×**、Pulse **4.9×** |
| **单个大文件操作** | Pulse | **已追平 Explorer**（5.78 vs 5.89 s）；优化前落后 2.2×，CPU/GiB −78% |
| 文件查找 | Pulse（冷搜） | 三者同量级，ZenFile 居中间 |
| 大量文件加载 | **ZenFile**（0.481 s） | 领先，且内存最省 |
| 文件夹大小计算 | **ZenFile**（0.565 s） | 领先，峰值内存 1/8 |
| **目录复制前扫描** | **ZenFile** | **13×**（3.07 → 0.233 s），无三方对照 |

**一句话**：ZenFile 的优势在小文件批处理、冷启动加载、内存占用；
**曾经唯一的短板（单个大文件的连续写入）已经修掉**；
**第三个短板（整棵大树复制前的规划扫描）也修掉了，13 倍**。

## 测试中发现并修复的缺陷

**缺陷 1：Alt 组合快捷键全部失效。** `main.rs` 只处理 `WM_KEYDOWN`，
而带 Alt 的组合键走的是 `WM_SYSKEYDOWN`——所有 `Alt+←/→/↑/↓` 与 `Alt+Enter`
（打开属性页）都没反应。补上 `WM_SYSKEYDOWN` 后修复。

**缺陷 2：`transfer.rs` 的分块粒度与注释不符。** 代码里做了 `clamp(块数)`，
导致块长被压到 74 MB，与注释描述的 8 MB 不符。第一轮修复它把 CPU/GiB 降了 37%，
第二轮才找到真正的病根——**用户态双拷贝路径本身**。
