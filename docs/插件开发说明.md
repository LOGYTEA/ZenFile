# 第一部分：5 分钟做出第一个插件

这一部分是**能照着做完**的操作路径。第二部分才是设计原理，不需要先读。

## 第 1 步：建目录

在 `ZenFile.exe` **同级**建 `plugins/<你的插件id>/`，里面放 `plugin.json`：

```bash
# Git Bash。路径按你的实际安装位置改。
EXE_DIR="/c/Users/Administrator/Desktop/project/File/workspace/target/release"
ID="hello-demo"
mkdir -p "$EXE_DIR/plugins/$ID"
```

> ⚠️ 目录必须在 exe 旁边，**不是 exe 的工作目录**。放错位置面板会显示「没有找到插件」。

## 第 2 步：写 plugin.json

在 `$EXE_DIR/plugins/hello-demo/plugin.json` 写入（**UTF-8、无 BOM、不加注释**）：

```json
{
  "id": "hello-demo",
  "name": "你好插件",
  "description": "第一个插件，用来验证心跳链路",
  "protocol_version": 1,
  "autostart": true,
  "capabilities": ["core.log"]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✓ | 唯一标识，**只能用 `[a-z0-9_-]`**。会进管道名与命令行参数 |
| `name` | ✓ | 面板上显示的名字 |
| `description` | | 一行说明，显示在名字下面 |
| `protocol_version` | | 填 `0` 或省略 = 不校验。填了且 ≠ 1 则拒绝拉起 |
| `autostart` | | `true` = 宿主启动时自动拉起 |
| `capabilities` | | 申请的能力。**没申请的调用宿主直接拒** |

## 第 3 步：这就是全部

**插件不需要编译任何代码。** 因为插件是 `ZenFile.exe` 的另一个进程：

```bash
"$EXE_DIR/ZenFile.exe" --plugin hello-demo
```

宿主启动时会自动执行这一行。`plugin.json` 就是插件的全部。

## 第 4 步：验证成功

打开 ZenFile →「设置 - 插件」，应看到：

```
你好插件
运行中                    ← 关键：不是「启动中」，更不是「启动失败」
```

**唯一可靠的判据**（面板文字可能骗人，看日志）：

```bash
grep "\[beat\]" "$TEMP/zenfile_plugins.log" | tail -5
```

期望输出形如：

```
[beat] id=hello-demo now=139485015 last_beat=139484921 age_ms=94 greeted=true pipe=\\.\pipe\ZenFile.19304.hello-demo
```

逐项判读：

| 字段 | 期望值 | 不对说明什么 |
|---|---|---|
| `greeted` | `true` | `false` = 握手没完成，插件进程没连上 |
| `age_ms` | 远小于 `5000` | 持续涨到 5000 = 心跳断了，会被判「无响应」 |
| `pipe` | `\\.\pipe\ZenFile.<插件pid>.<id>` | 管道名含插件自己的 pid |

### 退出码：定位失败在哪一步

插件进程自己退出时，退出码直接告诉你是哪一步挂了：

```bash
"$EXE_DIR/ZenFile.exe" --plugin hello-demo; echo "EXIT=$?"
```

| 码 | 含义 | 怎么办 |
|---|---|---|
| `0` | 正常收到 `shutdown` | 宿主主动停的，正常 |
| `2` | `--plugin` 后面没有合法 id | 检查命令行 |
| `3` | 管道连不上 | 宿主那边没建管道，或宿主已经退了 |

> 手动跑时**几乎总是 `3`**——管道名含插件自己的 pid，手动跑的这个进程没有宿主为它建管道。
> 退出码 3 要在**自动路径**下才有意义，别拿手动跑的结果下结论。

# 第二部分：设计原理

## 一句话

插件是 **`ZenFile.exe` 的另一个进程**，不是独立 exe，也不是 DLL，更不是 hook。

```
ZenFile.exe                     ← 宿主：窗口、托盘、文件操作、插件生命周期
└── ZenFile.exe --plugin <id>   ← 插件：独立进程，崩了不影响宿主
```

## 为什么这样设计

| 需求 | 做法 | 原因 |
|---|---|---|
| 插件崩了不能带崩宿主 | 每个插件一个**进程** | 进程间无共享地址空间，panic / 越界 / 死循环都碰不到宿主 |
| 不要一堆 exe 要单独升级 | 同一个 exe + `--plugin <id>` | 升级一次到位，协议版本永远一致 |
| 宿主退了不能留孤儿 | 全部挂进同一个 **Job Object** | `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`，句柄一关内核自动终结全部子进程 |
| 插件卡死也要能发现 | **心跳 + 超时**（5 秒） | 进程还活着不代表有用——死循环、弹了个模态框都算卡死 |
| 插件别跑在 Job 之外 | `CREATE_SUSPENDED` → 入 Job → `ResumeThread` | 拉起即入组，杜绝「已跑起来才入组失败」的窗口期 |

**明确不提供**：hook 宿主内存、装 API hook、读宿主函数表。
想要新功能就改宿主代码重新编译，而不是塞一段机器码进去。

## 协议与消息格式

管道名由 **插件自己的 pid + id** 决定：

```
\\.\pipe\ZenFile.<pid>.<safe_id>
```

用 pid 是为了让「重启同一个插件」天然换一条管道，不会撞上上一条的残留。
两侧**必须调同一个函数** `zenfile_core::plugin::pipe_name(pid, id)` 计算这个名字——
早期宿主侧直接拼原始 id、插件侧过滤过字符，id 带非安全字符时两边算出两个名字，插件永远连不上。

传输是**换行（`\n`）分隔的 JSON**，一行一条消息：

| `t` | 方向 | 载荷 | 说明 |
|---|---|---|---|
| `hello` | 插件 → 宿主 | `{"t":"hello","id":...,"protocol":1,"argv":[...]}` | 握手，声明身份与协议版本 |
| `beat` | 插件 → 宿主 | `{"t":"beat"}` | 心跳 |
| `shutdown` | 宿主 → 插件 | — | 插件收到后应干净退出，返回 `0` |
| `call` | 宿主 → 插件 | `{"t":"call","id":N,...}` | 一次能力调用，**必须回响应** |
| `result` | 插件 → 宿主 | `{"t":"result","id":N,"ok":bool,"payload":...}` | 对 `call` 的响应 |

### 三条必须遵守的协议纪律

1. **心跳必须自己主动发，不能等宿主来问**。宿主判断「插件还活着」的唯一依据就是这条。
   只在收到消息时才发心跳，宿主一安静就会误判卡死。间隔取超时的一半（`2500ms`），丢一拍不会被误杀。

2. **收到 `call` 必须回响应，哪怕回失败**。不回的话宿主那边挂着一个等不到的请求。

3. **读消息时半截 JSON 要留着等下一次**。管道是字节流，一次读拿到的很可能只是半条消息，
   直接解析会报 "EOF while parsing"——那不是协议错误，只是正常分片。

### ⚠️ 一个非常容易踩的坑

**`CreateNamedPipeW` 之后必须调 `ConnectNamedPipe`，否则数据永远不流动。**

`CreateNamedPipeW` 只是造出一个「待连接」的实例；客户端 `CreateFileW` 挂上来的那一刻
连接还在排队状态，要 `ConnectNamedPipe` 才真正接通。

漏掉这一步的现象**极具欺骗性**：管道看起来存在、插件进程活着、没有任何错误日志，
但宿主一个字节都读不到——心跳永远停在初始值，5 秒后被判卡死。
唯一的判据是看日志里 `last_beat` 是否在更新（见第一部分第 4 步）。

客户端可能在 `ConnectNamedPipe` 之前就连上了，此时返回 `ERROR_PIPE_CONNECTED(535)`——
那是**成功**，不是错误，别当失败处理。

## ⚠️ 当前限制

**能力调用链路（`call` / `result`）尚未实现。** 宿主侧读线程目前只认 `hello` 和 `beat`，
收到 `call` 不会真的分发给插件。

所以当前可验收的范围是：**装得上、看得见、进程能拉起、能握手、能持续心跳、崩了能兜住**。
不要在 `call` 上花时间。

同理，`crates/zenfile-core/src/ipc.rs` 里的长度前缀帧（4 字节 LE 长度 + JSON）与
`Envelope` 枚举**只在单元测试和自检里使用**，是给后续演进预留的正式帧格式，
**不是**当前生效的传输格式。

## 可申请的能力

| 字符串 | 含义 |
|---|---|
| `clipboard.history` | 读剪贴板历史 |
| `screenshot.capture` | 触发截图 |
| `taskmgr.snapshot` | 拉取进程/性能快照 |
| `terminal.open` | 在当前目录开终端 |
| `preview.open` | 请求预览文件 |
| `core.log` | 写一行日志 |

能力名**点号小写与 PascalCase 两种写法都收**（`clipboard.history` 与 `ClipboardHistory` 等价）。
写错时报错会列出全部可用名字：

```
未知能力 "no.such.cap"，可用：clipboard.history / screenshot.capture / ...
```

## 生命周期与状态机

```
                     discover()  整个进程只做一次
                         │
                         ▼
   清单损坏 ──────────► Failed  (面板可见，不静默跳过)
                         │
   协议不符 ──────────► Failed  "协议版本不兼容"
                         │
                    拉起进程 ──► 拿到 pid ──► 建管道 ──► ConnectNamedPipe
                         │
                    Starting ──── 心跳超时 ──► Hung ──► kill ──► 重启
                         │
                  收到 hello（greeted）
                         ▼
                      Running
```

面板上的六种状态（`PluginState::as_str()`）：

| 状态 | 含义 |
|---|---|
| 已禁用 | 你关掉了它 |
| 启动中 | 进程已拉起，还没握手 |
| 运行中 | 正常 |
| 已停止 | 进程没了，正在等重启 |
| 无响应 | 心跳超时，会被杀掉重启 |
| 启动失败 | 连续崩溃到上限，或清单/协议有问题 |

副标题按重要性三选一：出错原因 > 崩溃次数 > `description` > 纯状态。

### 崩溃处理

宿主在 **100ms 定时器**里检查：

1. 先判**进程还在不在**，再判心跳。顺序不能反——崩掉的插件 pid 还在句柄表里但已不存活，
   若先判心跳，一个已经崩了的插件会被记成「卡死 5 秒」，面板写「无响应」而真相是「已崩溃」，
   排查方向都被带偏。
2. 进程没了 → 崩溃计数 +1 → 按上限决定重启或放弃
3. **连续崩溃 4 次后停止重启**（`crashes > MAX_RESTARTS`，`MAX_RESTARTS = 3`，
   即实际重启 3 次）

上限是必须的：一个一启动就崩的插件（配置写错、依赖缺失）无限重启会变成
「任务管理器里 ZenFile 疯狂拉进程」的灾难，比崩溃本身更糟。

> 注：设置页底部固定文案写的是「最多 3 次」，与实际行为差 1 次，属已知偏差，排查时以面板实时显示为准。

### 启停

在「设置 - 插件」里开关。命中 action 编号 `1000 + 槽位下标`，再**按当前槽位顺序反查 id**
——不能拿配置 key 的下标，那份顺序与实际发现的顺序可能不一致。

清单损坏的插件不允许启动（它连 id 都没解析出来，进程参数凑不齐）。

## 能力边界

插件进程里**没有窗口、没有托盘、没有单实例互斥**（`main.rs` 的 `--plugin` 分支在那些逻辑之前就 return）。
它拿不到宿主窗口句柄、托盘、别的插件的管道。

## 排查

### 日志文件

宿主把插件现状写进 **`%TEMP%\zenfile_plugins.log`**：

| 前缀 | 时机 | 内容 |
|---|---|---|
| `[discover]` | 扫描目录时 | 每个插件的 id/name/state/pid/crashes/error |
| `[beat]` | **心跳变化时**（节流后约 2.5s 一行） | 心跳时刻、age、greeted、管道名 |

Windows subsystem 下 `eprintln!` / stderr 拿不到，写文件是唯一可靠手段。

> 判「管道通没通」只能看 `[beat]` 行的 `last_beat` 是否在变。
> **不能靠「没看到失败日志」反推**——那不叫验证，那叫没测。

## 常见问题

**面板显示「没有找到插件」**
`plugins/` 目录要和 `ZenFile.exe` 放在一起，不是 exe 的工作目录。

**面板显示「启动失败 · 读不到 ... plugin.json」**
清单路径不对，或 JSON 语法错误。`plugin.json` 必须在插件子目录里，不能写在 `plugins/` 根下。
注意文件必须是 UTF-8 无 BOM。

**面板显示「协议版本不兼容」**
`plugin.json` 的 `protocol_version` 与宿主对不上。宿主当前是 `1`，填 `0` 可跳过校验。

**面板卡在「启动中」，`greeted=false`**
管道建了但没通。查 `[beat]` 行的 `age_ms` 是否持续增长——增长就是没收到心跳，
十有八九是 `ConnectNamedPipe` 漏了。

**面板反复「已停止」→「启动失败」**
插件进程起来就退。手动跑一次看退出码：`3` = 管道连不上，`2` = id 非法。
